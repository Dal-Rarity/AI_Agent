## 本轮回归发现（2026-10-07）

**验证方式说明**：全部 35 个已执行场景均为真实 e2e（生产链路 build_unified_app + 心跳 + 回滚 + 裁剪 + 真实模型）；
场景 28/29/30 分别用变体任务打穿（28c 纯只读链、29b 20 文件写链、30d 协议 ACK），结构闸的触发均来自
生产中间件在真实模型交互中的自然产出，未使用任何脚本替代执行；场景 6 为已核实的设计缺口。

**全量重跑复核记录（stamp rr1a–rr7a）**：首轮未通过的场景 30（空转守卫 handoff 绕过）与
场景 33（错误链吞掉真实连接错误）修复后，35 个可执行场景于同日全部重新真实执行，35/35 通过。
重跑过程中的三条如实记录：①批次命令中的 `30d` 曾被 PowerShell 解析为 Decimal 字面量 `30`，
导致基础变体误跑一次（主管凭自身对齐拒绝撒谎、1 步结束，未产生假成功；后改单独调用重跑 30d 通过）；
②harness 校验器两处字面过窄已放宽：verify_26 的"如实汇报"同时接受"错误/失败"表述、verify_36 的
答案正则容忍运算符两侧空格——均为校验脚本问题而非系统缺陷；③29b 提示词补充"仅允许派遣一次"
约束（首轮重跑时模型把任务拆成多次派遣、每次均未触达 20 次硬上限，属模型非确定行为，
约束后单派遣内自然触发 L3[完成-待验证]）。

**首轮发现的问题（全部闭环）：**

1. ✅ **已修复**（场景 33，重测 fix33d / 重跑 rr6a 验证）：~~mysql_tools 错误链掩盖真实异常~~
   get_connection 异常时返回错误字符串，execute_query 原样返回，工具函数用
   `result, rowcount = ...` 解包字符串 → `too many values to unpack (expected 2)`。
   修复：get_connection 连接失败直接 raise（并附明确 host:port），execute_query 不再用字符串哨兵。
2. ✅ **已修复**（场景 26/33）：~~L1b 连续错误闸前缀盲区~~ 真实错误文本为
   "数据库中的表查询错误："、"数据库查询错误："，不以"错误"开头。
   修复：`_is_tool_error` 增加包含式匹配 `"错误：" in text[:200]`。
3. ✅ **已修复**（场景 33）：~~数据源漂移无告知~~ 本轮以更严重的形式复现——模型直接篡改
   连接配置（见发现 7）；工具链端口由环境变量固定、无静默换目标通道，配置层守卫落地后
   漂移路径已全部封死。
4. ✅ **已核实生效**（场景 30/33 重测）：~~supervisor 层无空转守卫~~ 重测日志中主管节点
   两次真实产出 `[supervisor] [待办] 任务未执行…`，主管层守卫实际已挂载生效。
5. **心跳包装 docstring 与实现不符**：生产 _stream_with_heartbeat 超时后只打印，不 yield None。
6. ✅ **已修复**（场景 30 变体 d，重测 fix30a / 重跑 rr4c 验证）：~~空转守卫可被 handoff 工具调用绕过~~
   修复：①引导再调用的响应必须重新过守卫判定，仍无任务工具（仅 handoff）时直接合成二段
   `[待办]`，不进入下一轮图循环；②新增 `transfer_` 前缀识别，handoff 调用不计为任务工具。
7. ✅ **已修复**（新发现，场景 33 重测过程 stamp fix33c 实证）：**专家可直接篡改运行配置**——
   模型排障时自行将 .env 与 .env.example 的 `MYSQL_PORT=3308` 改为 3306（已人工恢复），
   若 MCP 重启将数据源漂移到 Windows 本机 MySQL83。修复（双层守卫）：
   ①MCP 命令入口（execute_powershell_command / run_powershell_script）检测"受保护配置 +
   写入意图"直接拒绝；②LangChain 写文件工具（write_file/copy_file/move_file）命中
   .env/.env.example 直接拒绝。守卫经函数级自测 7/7 通过；fix33d 与 rr6a 轮次模型未尝试改配置
   （故 e2e 未触发拦截），均选择如实上报并把配置变更决策权交还用户。
8. **VirtualBox NAT 链路假象**（环境事实，harness 已适配）：容器停后 VM 内 3307 无人监听，
   但 Windows 侧 VBoxHeadless 的 NAT 套接字仍占着 3308 接受 TCP 握手，数据转发被 RST，
   pymysql 只拿到语义歧义的 `(2013) Lost connection`，模型易误判为"端口配置错"而非
   "MySQL 未启动"。harness 已在停/启容器时同步删除/重建 NAT 规则（mysql-docker），
   使故障真实表现为 `(2003) Can't connect`。
